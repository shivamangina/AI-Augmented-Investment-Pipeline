# Process

This repo was built with Claude Code (Sonnet 5) as a pair-programming agent
for the full session — planning, code, tests, and this document's factual
sections. The sections below are split deliberately: engineering decisions
(factual, verifiable against the code and git history) versus personal
reflection on the working process (left for the human author, not the
agent — see the note at the bottom).

## Decisions made, and why

1. **Stack**: FastAPI + OpenAI API, Python — specified upfront by the
   author, not derived.

2. **Sourcing scope (YC + HN + Product Hunt)**: the assignment explicitly
   says *"pick one or two sources and go deep"* and separately lists *"a
   12-source sourcing layer where each source returns 2 garbage results"*
   as an anti-pattern. The agent flagged that three sources risks reading as
   shallow multi-sourcing rather than depth, and proposed narrowing to
   YC + HN. The author chose to keep all three anyway. Mitigation built into
   the code: Product Hunt requires a free developer token and fails open —
   `app/sourcing/producthunt.py` logs a warning and returns `[]` if the
   token isn't configured — so YC + HN remain the reliable, "gone deep"
   core, and PH is strictly additive when configured, not load-bearing.

3. **Thesis**: "AI Agents & Infrastructure for SMBs" (`app/thesis.py`) —
   chosen to match the assignment's own example query, and written as an
   explicit weighted rubric with a "why now" argument and named
   disqualifiers, not a one-line vibe ("good companies" is called out in
   the assignment as an anti-pattern).

4. **Score design**: the final 0–100 score is a computed weighted formula
   over four LLM-produced sub-scores (team 25%, product 30%, market 25%,
   risk-adjustment 20%), not one holistic number the model picks. This
   trades a little model flexibility for auditability — a partner can see
   exactly which dimension drove a score, and the math is unit-tested
   independently of any LLM call (`tests/test_thesis_scoring.py`).

5. **Memo rendering is deterministic, not a third LLM call**: memos are
   rendered from the analysis-stage JSON via a Jinja2 template
   (`app/recommendation/memo.py`), not generated by prompting the model
   again. This means a memo can't drift from or embellish beyond what the
   analysis stage actually said, and it keeps the three stages independently
   replayable — memos can be regenerated from committed `analysis/*.json`
   with zero API calls (`--skip-sourcing --skip-analysis`).

6. **Verified external APIs live before coding against them**, rather than
   relying on remembered/documented endpoints. The commonly-referenced
   public YC Algolia search key (used in a lot of older open-source YC
   scrapers) turned out to be dead (403 Invalid API key) when tested via
   curl. Switched to YC's own `api.ycombinator.com/v0.1/companies` endpoint
   instead, confirmed working, and used that as the actual sourcing
   mechanism. `app/sourcing/yc.py`'s docstring reflects the real endpoint,
   not the first one considered.

7. **Failure handling**: every sourcing adapter and every per-candidate
   analysis call is wrapped to degrade gracefully — log a warning and
   continue (skip that source, or skip that one candidate) — rather than
   raising and killing the run. Directly serves the "robust to bad or
   missing data" grading criterion: a broken Product Hunt token or one
   malformed OpenAI response shouldn't cost the other 14 memos.

8. **Testing scope is targeted, not exhaustive**: unit tests cover the parts
   with actual logic — dedupe/merge, the scoring formula, memo rendering,
   and the pure parsing/ranking helpers in sourcing — using fixtures and a
   mocked OpenAI client. No test needs network access or an API key, so the
   suite runs the same for a reviewer as it did during development.

## Real trail

- Git history in this repo is incremental and chronological — commits were
  made as each stage was actually finished (scaffold → sourcing → analysis
  + recommendation → pipeline/CLI/API → docs), not squashed or reconstructed
  after the fact. `git log --stat` shows the real build order.

  the actual prompt/template artifacts used at runtime, committed as-is.
